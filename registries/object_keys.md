# 私有产物对象键注册表

> 权威来源：架构方案"OSS + CDN：公开内容与用户私有产物**分 bucket**（私有走临时凭证）"；
> 落地裁决 2026-08-30 晚（用户）：私有产物放阿里云 OSS 私有桶，业主用**签名链接**打开。
> 纪律：**只增不改**——键是写的一侧与读的一侧之间的协议，改键等于把已经存在的产物变成孤儿。
> 新增走 PR 评审。

## 为什么要有这张表

私有产物**写的一侧与用的一侧不是同一个仓、也不是同一种语言**：册由 reportrender（Python）写，
链接由 project-svc（Java）签。两边谁也不能 import 谁，只能靠**同一条键**接头。
键写在这里，两侧各持逐字副本并各有一条守门测试盯住——对不上就是接不上头，不是风格问题。

**键是确定性派生的，不是分配的**。因此"这份产物出没出来"直接问存储即知，
不必另立一张台账去记"哪个 id 对应哪个对象"——台账会与真相漂移，派生不会。

## 桶

| 用途 | 桶 | 访问 |
|---|---|---|
| 用户私有产物（上传的户型图、解析产物、报告册、为他生成的图） | 私有桶（配置项 `ISHOME_OSS_BUCKET_PRIVATE`） | 桶级私有；对外一律**签名链接**，链接自带有效期 |
| 公开内容（内容工厂的公开图集） | 另一只桶，**不在本表射程内** | 公开读 + CDN |

**分桶是红线不是优化**：用户上传的户型图、解析结果、为他出的图与册一律私有产物，
不进公开内容库、不被其他用户复用（获客线红线二）。桶权限是这条红线唯一靠得住的执行点——
同一只桶里靠前缀分公私，改错一次 ACL 就全公开了。

## 键

| 产物 | 键 | 写的一侧 | 用的一侧 |
|---|---|---|---|
| 报告册（单册自包含 HTML） | `reports/{report_id}/book.html` | reportrender-svc（activity `report-book-render`） | project-svc（签发链接） |
| 用户上传的图（原件） | `uploads/{content_sha256}/original.{ext}` | channel-svc（渠道 adapter 收到图即取下来落桶） | 生成侧解析（activity `floorplan-parse`，吃对象键不吃本地路径） |

`{report_id}` = ULID 26 字符，由 project-svc 在派发前铸（铸在派发之前，重试才有幂等键可握）。

`{content_sha256}` = **图片字节的 SHA-256 十六进制小写 64 字符**，`{ext}` ∈ `jpg` / `png` /
`webp` / `gif` / `bmp`，由**字节首部判定**（不认字节就整条响亮失败，不按渠道给的文件名猜）。
键里三样东西都不许出现，各有各的理由：

- **用户标识**（open_id、user_id）——生成侧不知用户是谁是红线，而键是生成侧的入参；
- **渠道方言**（飞书 `image_key`、`message_id`）——方言只存在于 adapter 与 `raw_payload`；
- **新铸的流水号**（ULID）——渠道事件会重推，铸一次就多一个对象；重推那次被入站幂等挡下，
  多出来的对象永远没人认领。

**取内容自身作键把这三件事一次解决**：同一张图重推多少次都写同一个键、同样的字节，天然幂等；
键里没有任何身份与方向信息；而"这张图在不在桶里"照样问存储即知。代价是重推会多下载一次
（幂等去重在下载之后），不留孤儿对象，可接受。

**同图撞键是特性不是冲突**：两个人发同一个文件落同一个对象——而想知道这条键得先有这份字节，
猜不出来。谁传的这件事记在渠道侧的入站消息记录里，不写进键。

`original` 这个名字说的是"用户发来的那一份"，给同一份上传件的派生物（解析产物等）在
`uploads/{content_sha256}/` 下留了位置；派生物的键**未定，用时再进本表**。渠道侧不给它起
语义名（不叫 `floorplan`）——**渠道层不理解语义**，这是不是户型图由后面的步骤判。

**同一份报告重跑覆盖同一个对象**，天然幂等；要留历史版本另立键，不在当前射程
（触发条件写死＝出现"同一份报告要并存多版给业主对比"的需求时）。

## 内容类型

册写入时带 `Content-Type: text/html; charset=utf-8`——签名链接不改这个头，
写的时候写错，业主点开看到的就是一屏源码。
